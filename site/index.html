DOCUMENTATION

Prose that can’t quietly go stale

An AI wrote the sentence once. Arithmetic checks it forever.

A diagram can’t drift from the schema, because it’s generated from it. Prose can, and always does. So vibeX documents a system the same way it draws one — the unit isn’t a page, it’s a claim: one sentence with a source attached.

DERIVED

Computed from the spec

One of ten fixed generators reads a diagram spec and writes the sentence. It cannot disagree with the diagram beside it, because it is the diagram.

ANCHORED

Pinned to a file and a symbol

Held by a content hash that ignores whitespace. Reformat the file and nothing moves. Change the line and the claim flags itself.

ASSERTED

A person’s decision, dated

For what no file can prove. Carries the name and the date, and it expires — so “we decided this in March” can’t pass for fact forever.

Confidence is computed, never written

A claim cannot declare how trustworthy it is. The build assigns one of five states from the evidence and the clock, and the validator rejects any claim that tries to rate itself.

verified stated needs re-reading out of date unverifiable

There is no model in the verification path — only fs, path, crypto and git. That is why a full drift check costs about 70 milliseconds and nothing per run.

$ vibex docs system.docs.json specs/ \
    --repo . --check
  59 claims — 54 verified, 5 stated,
  0 stale, 0 broken, 0 expired
  # after someone edits the guard
  needs re-reading  order-guard
  exit 1

It tells you what it doesn’t cover

Every document renders three lists: what was read, what is deliberately out of scope and why, and what the build noticed but could not account for. A document that implies completeness gets believed exactly where it is wrong.

One artefact, two readers

People read the dashboard panel. Agents read docs.json — every fact once, addressable, with resolved edges, so “what breaks if I change this” is a single lookup rather than a search.

One document per question

auth.docs.json, payments.docs.json — each becomes its own entry. Not one document trying to be the whole system and succeeding at none of it.

Markdown that travels

--md emits zero raw HTML, so a document survives a paste into Confluence, a wiki or a README. CI fails the build if a single tag escapes.

What it does not do

It catches drift, not initial error. If the first draft misreads the code, the hash still matches, CI stays green, and a wrong claim can stay verified indefinitely. Reviewing the spec once, at authoring time, is the only thing that establishes truth.

The honest version of the pitch: you get a reviewable first draft in one pass, and after you have read it once, arithmetic keeps it honest.

Three commands. No config file.

Point it at a schema you already have. If there isn't one, it reads the code — NestJS controllers, GraphQL resolvers, TypeORM entities — and writes the spec itself.

01

Import

Your schema becomes a draft spec in one pass. Then you edit it like a human — rename groups, drop the health check.

$ vibex import prisma
  schema.prisma db.erd.json
02

Validate

Dangling references and unreachable states are errors that name the field. Layout gripes are warnings that never block you.

$ vibex validate db.erd.json
  ok — 18 entities
03

Render

One HTML file, CSS and JS inlined, spec embedded. Or roll every spec in a folder into a single dashboard.

$ vibex render db.erd.json
  db.erd.html

INSTALL IT AS A SKILL

Stop learning flags

INTAKE

Wrong? Fix it from where you found it.

Every claim and every node carries a report link. It opens an issue with a fenced vibex block naming exactly what the reader was looking at — so the request arrives with its coordinates attached instead of “the auth docs seem wrong”.

It answers either way

Actionable or not, the issue gets a reply and a label. An intake queue that answers nothing is worse than no intake queue.

It cannot assert its way out

The agent follows the same SKILL.md you do. If it could not establish something from the code, that goes in coverage.out_of_scope — not into a claim under somebody’s name.

It opens, it never merges

The change arrives as a pull request that has already run validate and docs --check. A human still reviews it.

It tells you how it grouped things

If the history doesn’t use conventional-commit prefixes, the sections are inferred from the files each commit touched — and the output says so, in the document: “treat the grouping as a rough sort, not as the author’s intent.”

Two outputs, same source

-o changelog.json for the dashboard panel, --md CHANGES.md for the repository. Commit links resolve to your remote.

PRIVATE BY DEFAULT

The security review is one sentence long.

An architecture diagram is a reconnaissance map of your system — table names, service topology, auth boundaries, every internal route. It is the exact thing you cannot paste into someone else's SaaS.

So vibeX doesn't have a server. No vendor, no DPA, no subprocessor list, no questionnaire. There is nothing to review, because there is nowhere for it to go.

What the generated file does not do

  • No fetch, XMLHttpRequest or WebSocket, anywhere in the viewer runtime
  • No CDN, no web fonts, no analytics, no telemetry — the system font stack and nothing else
  • PNG export renders through an in-memory blob; it never touches the network
  • Pull the cable out of the wall and it still pans, zooms, searches and exports

vibeX documents a service well today. The work in front of it is what happens when you have thirty — one map whether they live in one repository or thirty, and the ability to follow a single request across all of them.

Request workflows

Follow one request across service boundaries — the call in, the services it touches, the events it publishes, the tables it writes. C4 shows what could talk to what. This shows what actually happens when somebody presses buy.

COMING SOON

Don’t want to run any of this? We’ll run it.

Connect the repository once. From then on the compute happens on our infrastructure on every build, the document is rebuilt against the commit that just landed, and it is never out of date. No CI job to wire, no bucket to own, no SSO rule for somebody to remember, no drift check to go green on a machine nobody is watching.

Yes — this one reads your code

It has to. We are running the build, so we check out the repository the same way your CI would. We would rather say that in the first line than have you find it in a permissions dialog.

What happens to it is the part that matters: the checkout is read inside an ephemeral build and discarded when the build ends. What persists is the generated document — the claims, their sources and their confidence. We do not keep a copy of your source, and we do not train anything on it.

WHAT WE ARE BUILDING TO

Encrypted, and audited as such

In transit and at rest, with the evidence a compliance review actually asks for rather than a badge on a marketing page. We do that work once so that nobody on your side has to do it per team.

Behind your identity provider

Read-only for every viewer

The hosted document renders. Nobody reading it can edit a claim, re-anchor a hash or mark something verified — the only thing that can change it is your next build.
